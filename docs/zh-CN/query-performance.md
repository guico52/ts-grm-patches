# 补丁性能核查

## 当前 API 性能审查（2026-11-27，四点打磨之后）

本轮将 Git HEAD `7ce7fad` 在临时目录单独构建，与当前未提交实现同机比较；未改运行时代码。旧基准对两版分别正序、反序运行。新增表达式基准比较字段链式、q.fn、仅原型增强及自动分析，并把表达式构造、查询构造、同步 Fragment 生成、预构建查询 fetchList、完整构建及 fetchList 分开测量。各模式均断言 SQL 和参数一致。

结论：删除逐实例链式包装显著减少了 q.fn 表达式与分组查询的构造成本；新增原生链式方法没有使普通字段构造变慢。完整 client 增强与 autoGroupBy 仍有微秒级成本，便携函数每次渲染仍须降级，不能描述为零开销或保证端到端无感。

### 与旧实现同机对照

单位 μs/次；区间为两轮中位数范围，非置信区间。

| 场景                               |      旧实现 |    当前实现 |
| ---------------------------------- | ----------: | ----------: |
| q.fn SUM + 1 表达式构造            |  9.27–39.08 |   0.35–0.40 |
| q.fn 分组查询构造                  | 20.90–30.30 |   6.71–6.81 |
| autoGroupBy 分组查询构造           | 23.65–35.00 | 13.59–19.94 |
| 普通增强查询构造，无 q.fn/自动分析 |   2.90–3.99 |   3.39–4.76 |

表达式构造在两轮配对中减少约 96%–99%，q.fn 分组查询构造减少约 68%–78%。普通增强查询仍要安装查询/投影方法并遍历语义，未观察到同等降幅。原型安装后的原生 SUM + 1 仍约 0.02–0.04 μs。

全套样本中简单查询 autoGroupBy 曾出现当前构造时间高于旧版，因此又按“旧、新、新、旧”单项复测。旧版中位数为 6.26/6.94 μs，当前为 6.00/6.17 μs；本轮未复现稳定退化。完整 fetchList 管线波动更大，不能从其中一轮的单点差值断言渲染性能回归。

### 新数学链式与真实渲染阶段

以 `amount.sum().abs().round(2)` 为例，原生参照使用产生相同 SQL 的 native 模板。仍为 μs/次：

| 使用方式                             |  查询构造 | 预构建查询的同步 Fragment 生成 |
| ------------------------------------ | --------: | -----------------------------: |
| 原生 client + 等价 native SQL        | 0.19–0.23 |                    14.64–16.69 |
| 仅 applyPatches + 字段链式           | 0.99–1.08 |                    19.58–22.61 |
| 增强 client + 字段链式               | 4.49–5.02 |                    19.14–22.99 |
| 增强 client + q.fn                   | 4.91–5.35 |                    17.84–20.75 |
| 增强 client + 字段链式 + autoGroupBy | 7.66–8.02 |                    17.83–22.38 |

仅数学表达式构造，字段链式为 0.81–0.87 μs，q.fn 为 0.94–0.97 μs。便携函数增加的渲染工作仍然可测；字段链式和 q.fn 最终共享实现，不应把不同进程中数微秒的波动当作某种语法稳定更快。自动分组在构造时分析，不会在每个返回行或每次 Fragment 生成时重新执行。

同步阶段使用原生公开 SPI `Composite.of`，涵盖 PreVisitor 与 FragmentGen，不含 SQL 字符串拼装、执行器及网络。另保留了预构建/完整 fetchList 管线的数据。PostgreSQL 的 trim/left 样本未显示稳定的大幅渲染退化，但不能由此推断另外四种方言及复杂展开函数的成本。

### 仍值得优化的代码位置

1. 查询与投影每次创建时仍定义方法和闭包，普通增强 client 的固定成本尚在。频繁新建 client 还会重建函数上下文；应复用 client。
2. 便携节点缓存的是 profile 对应的函数集，每次渲染仍构建临时降级节点和 parts。复用表达式可省构造成本，不能省掉这一步。
3. 字符串 NodeRender 的成功路径仍创建缓冲操作和重放闭包；接管路径仍创建 profile 与完整字符串函数集，length 接管还创建便携函数集。SQLite pad 还可能先抛不支持异常再接管。这是后续优化重点；本轮未测其复杂展开在数据库服务端的执行成本。
4. 方言校验与 autoGroupBy 会分别遍历表达式，where/orderBy 的即时校验与 finish 校验也有重复。保留 fail-fast 语义的前提下可考虑按一次查询生命周期复用分析结果。

全局新增缓存使用 WeakMap/WeakSet，分析用的强 Map 限于单次查询，未发现按 SQL 文本无限增长的新增缓存；这只是静态检查，不是持续负载泄漏测试。第一次 applyPatches 的样本约 0.5–1.3 ms，不包含包导入/模型初始化，不应把它摊为每次查询成本。

主机同时有桌面/浏览器进程活动，全部数据为本机微基准，没有测实际数据库、网络、非空结果解码、持续堆占用或 p95/p99。若某生产负载每查询增加 10 μs CPU，则 10,000 次/秒约增加 0.1 核 CPU 的需求；这是量纲换算，不是本轮端到端实测。

## 结论

补丁不是零开销。普通导入未自动修改原生 API；基础 applyPatches 在普通字段查询上的稳态影响较小。显式 enhanceClient 或使用补丁的 newSqlClient 后，即使没有调用 q.fn、autoGroupBy，每次查询仍增加实例方法安装、生命周期检查和方言校验。q.fn 返回表达式的逐实例链式增强是本例最大的额外 JavaScript 成本。

自动分组在查询构建回调结束时执行，不会针对返回的每一行重新分析。执行器、连接池和事务仍由原生 client 处理；但使用展开的方言函数、改变过滤器或分组规则会改变 SQL，数据库端的成本需要另测。

## 方法与复现

```bash
pnpm bench:query
# 反向排列模式顺序再跑一次，检查顺序效应：
pnpm build

```

环境为 Linux x64、Node v24.15.0、Intel Core i7-12700H。每种模式启动独立 Node 进程，避免全局补丁和 V8 调用点相互污染。预热后自适应批次数，每批目标至少 40 ms，取七次样本的中位数；保留 256 个结果的循环数组，让构建的对象逃逸计时循环。每次样本前主动 GC，计时内自然发生的 GC 仍计入。

以下区间为正序、反序两轮各自中位数的最小值与最大值，不是置信区间。raw 数据保留每批迭代次数、最小值、最大值和 SQL/参数。

- native：只加载原生包。
- imported：导入补丁包，继续使用原生 client，不调用 applyPatches。
- patched：调用 applyPatches，继续使用原生 client。
- enhanced-native：基础补丁加 enhanceClient，表达式仍使用原生 DSL，手写 GROUP BY。
- enhanced-functions：基础补丁加 enhanceClient，使用 q.fn 的链式表达式，手写 GROUP BY。
- enhanced-auto：与上项相同，改由 autoGroupBy 推导；普通查询也开启 autoGroupBy。

简单查询是选择 id/name、按 id 过滤；分组查询选择 UPPER(LOWER(name)) 和 SUM(amount) + 1，并按前者分组。测试使用真实 PostgresDriver 和原生 SQL renderer，执行边界返回空数组。脚本对六种模式生成的 SQL 文本及绑定参数做完全一致性断言。

因此 render 指“每次重新构建查询 + SQL 生成/绑定 + 原生 fetchList 管线 + 空结果模拟执行”，包含异步调用成本。它不包含网络、数据库实际执行、非空结果解码，也不是预构建查询反复执行的测量。导入时间、首次模型初始化、其他四库、复杂关联/CTE、持续负载堆占用、p95/p99 均未在本轮测量。

在这两个样本中，普通增强查询构建及 render 相对原生多约 12 μs；q.fn 分组查询多约 94–101 μs。后者约为原生本例的 4.2–4.4 倍，自动分组模式约 4.5 倍。这个倍数只适用于测到的 JavaScript 管线，不能直接套到有数据库等待的请求上。

同样需要看绝对成本：对于当前约 0.24 μs 的原生分组 AST 构建，增强后的几十微秒会产生很大的构建阶段倍数，但它不是数毫秒或数十毫秒的网络请求基准。两轮结果有噪声，不能把相邻模式的每个差值都视为稳定的独立组件耗时。

其他观测：

- 在相同 driver/entityManager 上新建并绑定 client 约 31–36 μs，原生 client 约 0.25–0.28 μs。前者会创建完整 fn 上下文，适合按应用配置复用；本轮未计入真实连接建立。
- 单独构建 SUM(amount).plus(1)，通过 client.fn 返回两个增强表达式时约 23–25 μs；原生路径约 0.02 μs。该结果只覆盖这个很小的表达式构造。
- applyPatches 后，新表实例首次访问 BOOL 与 TEXT 并构建两列投影，约 10.2–10.9 μs。原生 0.0.13 不支持相同查询，不能声称这是相对于可用原生实现的性能退化。
- BOOL/TEXT 在同一表实例缓存后不再触发异常回退；缓存读取微基准接近测量下限，不用于推导业务收益。新的查询表实例仍需要首次回退。

## 代码路径与 CPU 采样

以下描述优化前的代码。源码检查和额外的 enhanced-functions CPU 采样一致：表达式增强是显著热点，查询包装、函数上下文创建、方言校验也有采样。

1. 每个新函数结果都检查完整的方法清单，构造 Map、闭包和属性描述符，再执行 Object.defineProperties。一个链条有多个结果对象，会重复这一步。涉及 expression-chain.ts 的 createExpressionEnhancer。
2. 每个查询都安装 select/where/groupBy 等实例包装，并为投影再安装链式条件方法。即使没有使用增强函数，这条路径也会执行。涉及 query-enhancer.ts 的 enhanceQuery。
3. where/groupBy/having/orderBy 调用时验证方言，finish 时又统一遍历；validateFunctionDialects 还在每次调用时声明 Visitor 子类和创建实例。即使不启用自动分组也会发生。
4. inferGroupBy 在启用时分析 AST，创建 shape/Visitor 并验证分组键。当前分析 cache 保存结果，但 analyze 入口没有按上下文读取缓存；共享节点可能被重复分析。任何缓存优化必须区分 insideAggregate 上下文，保留嵌套聚合校验。
5. BOOL/TEXT getter 在每个新表实例第一次访问时先调用会抛错的上游 getter，再回退并写缓存。安装后的 tableClass 包装在其他模型上也有一次 WeakSet 检查。

CPU 采样涵盖初始化、多个基准阶段和脚本主动 GC，不能用它的 GC 百分比推断线上服务的 GC 占比。本报告只用采样辅助确认热点位置，不给出各组件的精确贡献百分比。

这些路径说明，后续优化的首要核验对象是逐表达式的方法/闭包安装，其次是每查询包装与重复方言遍历。此次核查保留现有校验和查询语义，未将错误检测关闭作为性能对照。

## SQL 层的额外边界

上述基准的 SQL 完全相同，因此没有测量新增方言展开式在数据库端的额外工作。例如 SQLite padding 生成重复填充串，SQL Server 字符长度追加标记，带 start 的查找可能重复引用子表达式；它们的执行成本取决于数据量、长度和执行计划。

全局过滤器还可能改变 SQL：addGlobal 给每个目标模型注册过滤器，会影响原生框架关联读取外键的优化条件；addGlobalFor 仅向匹配列的模型注册。这个差异应通过真实关联查询的执行计划验证，本轮没有给它估算百分比。

## 性能优先改写后的复测

在 be7dfd3 基础上调整实现，继续使用原基准脚本，按正序与反序各运行一轮。两轮的原生分组 render 对照为 25.9–28.0 μs，优化前为 29.4–29.8 μs，存在运行环境噪声；以下改进比例是观测值，不是剔除了所有环境差异的精确归因。

| 测量项                              | 优化前，μs/次 | 优化后，μs/次 |
| ----------------------------------- | ------------: | ------------: |
| 增强 client，普通查询构建           |     8.78–8.97 |     2.55–2.68 |
| q.fn SUM(amount).plus(1) 表达式构建 |   23.26–24.78 |     7.10–7.24 |
| q.fn 分组查询构建，手写 GROUP BY    |   67.61–69.79 |   17.69–17.78 |
| q.fn 分组查询构建及 render          | 123.62–130.07 |   51.69–53.56 |
| q.fn 自动分组查询构建及 render      | 131.80–134.29 |   58.70–60.87 |

本例 q.fn 分组构建及 render 耗时降低约 57%–60%，自动分组模式降低约 54%–56%。优化后的管线仍有额外成本；没有把结果解释为数据库查询或线上接口的加速比例。

具体变化：

1. 按原生 prototype 缓存原始方法和属性描述模板。实例自有方法不使用共享 plan；继承 getter 返回的实例绑定方法也不跨实例缓存。
2. 用共享 getter 延迟创建链式方法，首次访问后缓存在表达式的 WeakMap 状态中。方法提取后仍绑定原表达式，不需要预先创建所有方法的闭包。
3. 只为继续返回值的变换安装链式增强。比较和排序保留原生方法，q.fn 的完整函数入口及基于操作数的聚合/方言检查继续存在。
4. DialectValidator 类移至模块级，每次调用仍新建携带方言与 seen 集合的实例，保留立即校验和 finish 校验。
5. 查询原始方法改为直接取值，减少 setup 中的数组与 Object.fromEntries 分配。
6. 自动分组在一次分析内缓存节点 shape 与分析结果。复用缓存时，若当前处于聚合内部且子树含聚合，仍报告 NESTED_AGGREGATE，避免缓存绕过阶段约束。

描述模板缓存以 prototype 为 WeakMap key，表达式状态以表达式为 WeakMap key；没有建立按 SQL 文本增长的全局查询缓存。此次未做持续负载内存测量，不宣称具体堆占用降幅。
